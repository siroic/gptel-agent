** Template placeholders in agent files
Agent definition files may contain ={{VAR-NAME}}= placeholders.  They are
expanded by =gptel-agent-update= (via =gptel-agent--expand-templates=),
so the substituted values are computed once and stay stable for the
whole session — session values come from =gptel-agent--session-templates=.

Available placeholders:

- ={{AGENTS}}= — formatted list of the registered agents (name +
  description).
- ={{SKILLS}}= — the available-skills block for the =Skill= tool.
- ={{USER}}= — =user-login-name=.
- ={{HOME}}= — the home directory, normalized with *no* trailing slash,
  so write ={{HOME}}/bin= (not ={{HOME}}bin=).  Falls back to
  =(expand-file-name "~")= when =$HOME= is unset or empty.
- ={{HOST}}= — =system-name=.
- ={{CWD}}= — the current directory (=default-directory=, expanded and
  abbreviated to =~/...= form, *no* trailing slash).  The value is frozen
  at =gptel-agent-update= time for prompt-cache stability, so it does not
  follow later buffer/directory changes.
** Agent file discovery and transclusion
Directory scanning (=gptel-agent--update-agents=) accepts only *regular*
files whose basename matches =gptel-agent--agent-file-regexp= — plain
=.org= and =.md= files.  Consequently:

- Backup files (=foo.org~=), autosave files (=#foo.org#=) and lockfiles
  (=.#foo.org=) are ignored, so editing an agent file no longer registers
  bogus agents.
- Subdirectories of an agents dir are *not* scanned.  Shared or common
  documents therefore belong in a subdirectory such as =agents/common/=,
  where they cannot be mistaken for agents.

Org agent files may pull in shared content with =org-transclusion=
keywords, e.g. a body line =#+transclude: [[file:common/shared.org::*Section]]=.

- Keywords are resolved at parse time by
  =gptel-agent-parse-org-properties= (helper
  =gptel-agent--resolve-transclusions=), which calls
  =org-transclusion-add-all=.
- Relative =file:= links resolve against the directory of the *agent
  file*, not the current =default-directory=.
- Resolution happens *before* ={{VAR}}= expansion, so placeholders inside
  transcluded content are expanded too.  (Transcluded text is read-only,
  so =inhibit-read-only= is bound around the expansion.)
- Keyword properties such as =:only-contents= and =:level N= work as usual.
- An unresolvable keyword (missing file or unmatched target) signals an
  error naming the agent file — it is never silently skipped.
- Transclusion is skipped for metadata-only reads (the agent-list scan),
  which never look at the body, so directory scanning stays fast.

Both behaviours are covered by ERT tests in
=test/gptel-agent-parse-org-test.el=.
** Dynamic per-agent overrides for sub-agent launches
=gptel-agent-subagent-overrides= (in =gptel-agent-tools.el=) is a =defvar=
— *not* a =defcustom= — providing an override point for callers that need
to compute sub-agent configuration from their own context.

Its value is a plist mapping an agent-name *keyword* to a preset-style
plist of gptel settings:

#+begin_src emacs-lisp
(:gatherer (:backend "DeepSeek" :model deepseek-v4-pro)
 :executor (:backend "Claude" :model claude-haiku-4-5-20251001))
#+end_src

When =gptel-agent--task= launches an agent it splices the plist stored
under that agent's keyword into the settings handed to
=gptel-with-preset=, *after* the agent's own definition plist.  The
resulting precedence chain is:

: hard defaults < gptel-agent-preset < agent file < gptel-agent-subagent-overrides

Note that the =AGENT-TYPE= argument of =gptel-agent--task= is a *string*
(e.g. ="gatherer"=); it is converted to the lookup keyword with
=(intern (concat ":" agent-type))=, so the keys of this variable must be
keywords.

The variable is nil by default and has no effect unless bound.  It is
meant to be =let=-bound dynamically around a sub-agent launch — for
example by an integration that derives settings from per-heading
properties in an Org document — rather than set globally; use
=gptel-agent-preset= or the agent files for persistent configuration.

** AI-DO Make agent file tools buffer-aware (Read / Edit / Insert)
*** Origin
Discovered while investigating a =siro-orga= workspace report that
gptel sends on-disk file content even when the visiting buffer has
unsaved user edits.  The primary bug lives in gptel proper (tracked
in =gptel.org=: /Prefer modified visiting buffer over disk in
file-based context/).  This TODO covers the parallel issue in the
gptel-agent file tools.

*** Discussion highlights
All three agent file tools read directly from disk via
=insert-file-contents= and never consult visiting buffers:

| Tool   | Function                          | Location (approx)            |
|--------+-----------------------------------+------------------------------|
| Read   | =gptel-agent--read-file-lines=    | =gptel-agent-tools.el:~1029= |
| Edit   | =gptel-agent--replace-in-file=    | =gptel-agent-tools.el:~760=  |
| Insert | =gptel-agent--insert-in-file=     | =gptel-agent-tools.el:~883=  |

There are zero occurrences of =find-buffer-visiting=,
=get-file-buffer=, or =buffer-modified-p= in =gptel-agent-tools.el=.

Consequences:

- *Read* returns stale content when the user has unsaved edits in
  the visiting buffer — sub-agents reason on outdated text.
- *Edit / Insert* write to disk under the user's feet without
  reverting the visiting buffer, leaving the buffer and disk
  out-of-sync.  Next user save clobbers the agent's edit; or the
  agent's next Read sees the disk version that contradicts the
  buffer the user is editing.

*** Mission
Make the three tools buffer-aware:

1. *Read*: if =(find-buffer-visiting path)= returns a buffer, read
   from that buffer instead of disk.  Note whether the buffer is
   modified in the returned content (small annotation, so the LLM
   knows it's reading unsaved state).
2. *Edit / Insert*: detect a visiting buffer; perform the edit *in
   the buffer* (preserving point/mark/undo) and then save it,
   instead of writing the file and leaving the buffer dirty.
   Alternatively: write file, then =revert-buffer= the visiting
   buffer iff it was unmodified; refuse and surface an error if the
   buffer is modified (user has conflicting unsaved edits).

Pick one strategy for Edit/Insert — recommend the in-buffer edit
path because it composes with the user's undo history.
